# 工作流說明

這套工作流的出發點：AI 寫程式很快，瓶頸在人的檢查。所以重點不在讓 AI 寫更多，而在讓成果不需要人逐行檢查也信得過。做法是三件事：動工前搞懂系統與需求、實作時用測試當防弊、驗收時讓沒參與的模型來查。

## 一、前期規劃

| 問題 | 指令 | 做什麼 |
|---|---|---|
| 需求只有一兩句話 | `/teamai:grill-me` | 一次問一個問題，問到範圍、不做的事、驗收條件都能條列 |
| 需求明確但寫得粗 | `/pstack:sharpen` | 改寫成帶關鍵步驟與客觀驗收條件的任務 |
| 不懂既有系統怎麼運作 | `/pstack:how` | 先讀相關模組，避免撞上舊架構或重複造輪子 |
| 不懂某段程式為什麼這樣寫 | `/pstack:why` | 查 git 紀錄與相關文件，避免把前人的保護機制拆掉 |

## 二、中期實作

| 問題 | 指令 | 做什麼 |
|---|---|---|
| 要先定架構 | `/pstack:architect` | 先畫外框與分工，照專案裡最近的例子做 |
| 有幾種做法難以取捨 | `/pstack:arena` | 不同模型各做一版，交叉比較後取長處 |
| 行為可以用測試描述 | `/pstack:tdd` | 先寫會失敗的測試，看到失敗才寫實作 |
| 其他較大的任務 | `/pstack:poteto-mode` | 總管指令，依任務類型調度其他 skill |

## 三、後期驗收

| 問題 | 指令 | 做什麼 |
|---|---|---|
| 真的能跑嗎 | `/teamai:evidence` | 實際執行，逐條對驗收條件，附上輸出、截圖或錄影 |
| 驗證流程會重複做 | `/pstack:create-verification-skill` | 把人工操作步驟寫成 skill，之後自動照做並存證 |
| 會波及哪裡 | `/pstack:blast-radius` | 評估影響範圍，動到核心邏輯就請人仔細看 |
| 寫得乾淨嗎 | `/pstack:interrogate` | 交給不同模型找漏洞 |
| 跨廠牌再看一次 | `/teamai:cross-review` | 把改動平行交給本機的 Codex、Gemini、Grok 唯讀審查，結果逐條查證 |
| 只有 agy 或要審文件、圖片 | `/teamai:agy-second-opinion` | 用 Gemini 審一次，結果回原始資料驗證 |

## 四、無人看管

| 問題 | 指令 | 做什麼 |
|---|---|---|
| 交代過夜任務 | `/teamai:overnight` | 寫出完成條件、停損條件、權限範圍；預設只開 PR 不合併 |
| 留下決策紀錄 | `/pstack:show-me-your-work` | 記下試了什麼、為何失敗、怎麼驗證，隔天抽查 |
| 合併前多方實測 | `/pstack:swarm` | 派多個沒參與實作的 AI 實測，全數通過才合併 |

## 五、持續修正

| 問題 | 指令 | 做什麼 |
|---|---|---|
| AI 一再犯同樣的錯 | `/pstack:correct` | 改環境不改提示詞：寫成 linter 規則、測試或 CI 閘門 |
| 回顧 | `/pstack:ketchup`、`/pstack:reflect` | 整理這段時間的工作與教訓 |

## 信任曲線

自動化的程度要跟著證據往上，一階一階來。用 `/teamai:trust-ladder` 檢查專案目前在哪一階、下一階缺什麼。

1. 單一 AI，人全程看著，記下它在哪裡出錯。
2. 把重複的錯變成硬規則（linter、CI），不只寫在提示詞。
3. 交件必須附證據。
4. 同時開兩三個 AI，寫的和審的分開。
5. 睡前交辦任務，有非黑即白的完成與停損條件。這一階 AI 不能自己合併。
6. 過夜的 PR 都能直接合併之後，才開自動合併與自動進單。

## 兩種起手式

- 新功能、需求模糊：重心在動工前的釐清。token 用量低，適合剛開始導入。
- 舊專案、大量修 bug、重構：重心在自動驗收與防呆。token 用量高，專案要先有測試與 CI。

前段釐清需求、後段嚴格驗收，兩種可以接起來用。
