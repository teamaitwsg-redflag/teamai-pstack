# 過夜任務單

無人看管的工作，品質取決於交代得多清楚。任務單要寫到另一個沒看過這段對話的 AI 拿到也能照做、也知道什麼時候該停。

## 先確認能不能過夜

- 專案還沒到信任曲線第 5 階（見 `/teamai:trust-ladder`）時，先告訴使用者缺什麼，建議先把任務切小、有人在場時做。
- 完成條件寫不成「非黑即白」的任務不適合過夜，先用 `/teamai:grill-me` 問清楚。

## 任務單格式

```
任務：一句話
背景：為什麼要做，相關的檔案、issue、先前的決定

完成條件（全部達到才算完成，每一條都能客觀判定）
  1. …（驗證指令或操作）
  2. …

停損條件（任何一條發生就停下來，寫下狀況，不要硬做）
  - 同一個問題試了 N 種做法都失敗
  - 需要動到「不可以碰」清單裡的東西才能繼續
  - 測試原本就是壞的，或修到一半發現需求有矛盾
  - 花費超過（時間或 token 上限）

可以做：（分支名稱、可以改的目錄、可以執行的指令）
不可以碰：（正式資料庫、部署、密鑰、CI 設定、別人的分支、指定的檔案）

交付方式：開 PR 到 <分支>，不合併。PR 說明附 /teamai:evidence 的交件報告。
決策紀錄：全程用 /pstack:show-me-your-work 記下試了什麼、為什麼失敗、怎麼驗證。
```

## 規則

- 寫的 AI 不核准、不合併自己的 PR。合併由使用者決定，或在第 6 階由沒參與實作的 AI 實測通過後才自動合併。
- 不為了達成完成條件而跳過、停用或刪除測試，也不放寬檢查規則。做不到就停在停損條件。
- 「不可以碰」沒寫的東西，只要是難以回復或會影響別人的，一律當成不可以碰。
- 一張任務單只做一件事。有好幾件就拆成好幾張，各開各的分支。
- 遇到停損就停，在 PR 或決策紀錄最上面寫清楚停在哪裡、試過什麼、建議下一步，讓使用者早上一眼看到。

## 隔天的交接

使用者回來時先給三行：做完了哪些、停在哪裡、哪些地方需要他親自看（改到共用邏輯、繞了路、驗不到的部分）。細節放在決策紀錄，用 `/pstack:ketchup` 可以整理。
