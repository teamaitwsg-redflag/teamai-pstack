# 交件附證據

規則只有一條：說「完成」之前，自己把成果跑一次，並且看過輸出。別人（或別的 AI）說跑過不算。

## 依成果類型收集證據

| 成果 | 最低限度的證據 |
|---|---|
| 函式庫、後端邏輯 | 測試指令與完整輸出（通過數、失敗數）。新行為要有新測試，而且看過它在修改前是失敗的。 |
| bug 修正 | 修改前重現錯誤的輸出，加上修改後同一個步驟的輸出。 |
| CLI、腳本 | 實際執行的指令與輸出，至少含一個正常輸入和一個錯誤輸入。 |
| 網頁、App 畫面 | 實際開起來操作的截圖或錄影，含改動的那個畫面。只有單元測試通過不算。 |
| API | 實際請求與回應（狀態碼與內容），含一個失敗情況。 |
| 資料處理 | 輸入筆數、輸出筆數、抽樣比對，以及用程式算的加總或檢查碼。 |
| 文件、報告 | 轉出最終格式後逐頁看過；文件裡的數字用程式對過來源。 |
| 設定、基礎設施 | 套用後查詢實際狀態的輸出，不是套用指令的回傳訊息。 |

畫面類的驗證流程如果之後還會重複做，用 `/pstack:create-verification-skill` 把操作步驟寫成 skill。

## 做法

1. 列出驗收條件。沒有的話先向使用者要，或從任務描述整理出來請他確認。
2. 每一條找出對應的驗證方式並實際執行。
3. 輸出原文保存（貼在報告裡或存檔），不要改寫成「測試通過」四個字。
4. 有任何一條沒過或沒辦法驗，照實寫，不要用整體結論蓋過去。

## 交件報告格式

```
結論：完成／部分完成／未完成（一句話）

驗收條件對照
| # | 條件 | 怎麼驗 | 結果 | 證據 |
|---|---|---|---|---|
| 1 | … | 執行的指令或操作 | 通過／失敗／未驗 | 輸出節錄或檔案路徑 |

沒有驗到的部分：（為什麼沒驗、誰來驗、怎麼驗）
已知問題與風險：
改動範圍：（檔案清單；動到共用邏輯時附 /pstack:blast-radius 的結果）
```

## 不算證據的東西

- 「應該可以」「理論上會過」。
- 只讀程式碼得到的結論。
- 外部 AI 或 subagent 回報的「完成」。要自己重跑驗證。
- 被跳過、停用或加了例外的測試所得到的綠燈。
- 模擬出來的 API 回應或假資料，除非使用者要的就是模擬。
