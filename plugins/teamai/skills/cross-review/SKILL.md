# 跨廠牌審核團

寫的人不驗收自己的成果。Claude 寫的改動，要讓別家廠牌的模型來找漏洞，因為同一家的模型有相同的盲點。這個 skill 用一支腳本把這件事做成固定動作。

腳本在本 skill 資料夾的 `scripts/review-panel.sh`，以下用 `<panel>` 代表它的完整路徑。

## 審核的完整順序

外部審查要花額度與時間，所以放在自己的檢查之後：

1. 先自己驗：測試與實際執行通過（`/teamai:evidence`）。沒過就先修，不要拿壞的東西去審。
2. 動到共用邏輯時跑 `/pstack:blast-radius`。
3. 同廠牌不同模型的交叉審查：`/pstack:interrogate`。
4. 跨廠牌：本 skill。
5. 逐條查證，修正，重新驗證，回報。

小改動可以只做 1 和 4。跳過哪一步要在回報裡寫出來。

## 步驟

### 1. 看有誰可以用

```bash
<panel> --list
```

| 審查者 | 廠牌 | 唯讀的做法 |
|---|---|---|
| `codex` | OpenAI | `codex exec -s read-only`；執行模式是 `-s workspace-write`，只限副本、不連網 |
| `agy` | Google | `agy --mode plan` |
| `gemini` | Google | `gemini --approval-mode plan`（沒有 agy 時才用，同廠牌只跑一個） |
| `grok` | xAI | `grok --sandbox read-only`，只給讀檔工具並關掉上網 |

一個都沒有時，告訴使用者缺什麼、怎麼裝（見最後一節），然後只做 `/pstack:interrogate`，並在回報裡明說少了跨廠牌這一道。

### 2. 第一次用、或工具更新過：先做自我測試

```bash
<panel> --selftest
```

它會實際要求每個審查者建立檔案。合格的條件是檔案沒有出現，而且審查者回報它試過、被擋下來。寫得了檔的判不合格；答非所問、看不出有沒有試的判無法確認。這兩種都不要用，用 `--only` 排除，並告訴使用者。這一步不能用讀說明文件代替：各家工具的旗標常改，唯讀到底有沒有生效只有實測才知道。

### 3. 選一種方式送審

| 方式 | 指令 | 審查者能做什麼 | 什麼時候用 |
|---|---|---|---|
| 執行模式 | `<panel> --prove --repo <repo> --base main` | 在自己的隔離副本裡寫檔、跑測試。發現要附上跑過的指令與輸出 | 程式碼改動，而且專案在副本裡跑得起來。這是預設該用的 |
| 唯讀 | `<panel> --repo <repo> --base main` | 只能讀，只能提意見 | 文件與設定的改動、專案要連網或要密鑰才跑得起來、或執行模式的自我測試沒過 |

執行模式是照 pstack 的 `interrogate`：沒有實際跑過的發現不算。唯讀審查者沒辦法執行，它提出的每一點都標成【未驗證線索】，不是發現；你自己重現成功之後，才能把它升格成發現。

執行模式的細節：

- 第一次用、或工具更新過，先跑 `<panel> --selftest --prove`。它要求審查者在副本裡建檔、並嘗試寫到副本外，結果有三種：
  - 合格（結束碼 0）：副本裡的檔案有出現、副本外的沒有，而且工具自己的紀錄裡有一行寫著副本外那個路徑被拒絕。會把那行紀錄印出來。
  - 不合格（結束碼 1）：寫得到副本外，或副本裡也寫不了。
  - 未驗證（結束碼 3）：副本外沒有檔案，但找不到被拒絕的紀錄（可能根本沒去試）、回覆和檔案狀態矛盾、或審查者沒有正常結束。紀錄會保留下來並印出路徑。
  只有合格才可以用執行模式。不合格或未驗證都改用唯讀，並把結果告訴使用者。只看「檔案沒有出現」不夠，因為沒去試的審查者也會留下同樣的結果。
- 每個可執行的審查者各有一份副本，放在暫存資料夾，路徑寫在 `<審查者>.workdir`。副本只有 git 追蹤的檔案和沒被忽略的新檔，`.gitignore` 擋掉的東西（例如 `.env`）不會進去。
- 審查者不連網，也寫不到副本以外的地方。原本的工作區它碰不到。
- 目前只有 Codex 實測過可以這樣隔離。`--prove` 時其他審查者照舊唯讀，總表最後一欄會寫 `prove` 或 `read`。
- 專案如果要先安裝相依套件才能跑測試，副本裡沒有那些套件，而且審查者不能連網去裝。這種專案用唯讀，或先告訴使用者這個限制。
- 查證完把副本刪掉（`rm -rf` 那個 `.workdir` 裡的路徑）。

- 審未 commit 的改動用 `--uncommitted`（包含還沒 `git add` 的新檔），審分支用 `--base <分支>`，審現成的 diff 用 `--diff <檔案>`。
- 想指定重點加 `--focus "這次改了金額計算，請特別看進位與幣別"`。
- 只用部分審查者加 `--only codex,grok`。
- 每個審查者預設最多跑 20 分鐘（`--timeout` 可調）。同廠牌的備援是在第一批都結束後才上場，所以整輪最長是兩倍的時間。Bash 工具的 timeout 要設得比這個長，或用背景執行。
- 結果在 `<repo>/.teamai-review/<時間>/`：每個審查者一個 `.md`，總表是 `summary.tsv`，`.log` 是該工具的原始輸出。這個資料夾會自己忽略自己，不會被 commit。自己用 `--out` 指定時，要給空的或還不存在的資料夾，每一輪用新的。

結束碼：0 至少一個審查者完整審完；2 沒有任何一個審完（包含只有 `incomplete` 的情況）；3 沒有改動；4 改動裡疑似有密鑰，沒有送出。

遇到結束碼 4 不要想辦法繞過。`secrets.txt` 會列出是哪些檔案（不含內容；含原文的 diff 已經刪掉），把那些檔案指給使用者，先把密鑰或 `.env` 從改動裡拿掉。`.env.example`、`.env.sample`、`.env.template` 這類範例檔不會被擋。

### 4. 讀總表，再讀每一份結果

`summary.tsv` 的狀態有 `ok`、`incomplete`、`empty`、`failed(碼)`、`timeout`、`missing`。只有 `ok` 的才算審過。`incomplete` 是有輸出但沒寫到結尾的完成標記，代表審到一半就停了，內容只能當線索，不能當成審過。`failed` 的去看對應的 `.log` 與 `.md`（有些工具把錯誤訊息印在標準輸出），常見原因是沒登入或額度用完，照實告訴使用者，不要反覆重試。

### 5. 逐條查證

執行模式的發現都附了指令。到那個審查者的副本裡（`.workdir` 的路徑）把指令原樣重跑一次：輸出確實顯示問題、而且那個問題違反這份改動的用意，才留下；重跑不出來的丟掉，並記下丟了幾條。審查者說它跑過不算，你自己跑過才算。

唯讀審查者的【未驗證線索】：照它寫的重現方式自己跑一次。重現得出來，才把它列為發現；重現不出來或沒辦法跑，留在「未驗證線索」，不和發現混在一起。

每個發現都要回到程式碼或實際執行去查，分成三類：

- 屬實：寫一個會失敗的測試或實際重現，修正，再驗證。
- 不成立：寫出不成立的理由與依據。
- 無法確認：列給使用者。

兩家以上都提到的問題優先查。只有一家提到不代表是錯的，沒有任何一家提到也不代表沒問題。

### 6. 回報

```
審核團：codex（ok）、gemini（ok）、grok（missing）
跳過的步驟：（例如沒有跑 /pstack:interrogate，原因）

| # | 發現 | 誰提的 | 查證結果 | 處理 |
|---|---|---|---|---|
| 1 | … | codex、gemini | 屬實（重現方式） | 已修，測試名稱 |
| 2 | … | grok | 不成立（依據） | 不處理 |
| 3 | … | gemini | 無法確認 | 請你決定 |

未驗證線索（唯讀審查者提的、還沒重現成功的）：
- …（誰提的、為什麼沒能重現）
丟掉的：每個審查者各丟了幾條、為什麼（例如重跑不出來）

修正後重新驗證的結果：（測試輸出）
審查紀錄：<資料夾路徑>
```

## 規則

- 審查者不碰原本的工作區：唯讀時只能讀，執行模式時只能動它自己的副本。不讓外部 AI 動手修，也不照著它給的修補程式直接貼上；修正由主對話做，做完自己驗。
- 外部 AI 說「沒問題」不等於通過，它只是其中一道檢查。
- 最終數字、資料庫寫入、部署、push 不交給審查者。
- 密鑰、.env、含個資或客戶資料的檔案不送審。腳本會擋常見的密鑰格式，但擋不了個資，送審前自己看一眼改動的內容。
- 審查者會讀到 repo 裡的其他檔案（執行模式是讀到副本裡的）。repo 裡有不能外流、又被 git 追蹤的資料時，不要用執行模式，改用 `--diff` 並把工作目錄指到只放那份 diff 的空資料夾（`--repo <空資料夾>`）。

## 安裝與登入

安裝與登入都要使用者同意，登入由使用者自己在終端機完成，不替他輸入密碼或授權碼。

| 審查者 | 安裝 | 登入 |
|---|---|---|
| codex | 裝 ChatGPT／Codex 桌面版就有（腳本會自己找到 App 內附的 CLI），或 `npm install -g @openai/codex` | `codex login` |
| agy | macOS、Linux：`curl -fsSL https://antigravity.google/cli/install.sh \| bash`；Windows 見 `/teamai:agy-second-opinion` | 在終端機執行 `agy`，依畫面用 Google 帳號登入 |
| gemini | `npm install -g @google/gemini-cli` | 只適用 API key 或企業帳號。個人 Google 帳號登入已被 Google 停用（2026-11 實測，錯誤訊息要求改用 Antigravity），個人帳號請裝 agy |
| grok | `curl -fsSL https://x.ai/cli/install.sh \| bash` | `grok login`（需要 SuperGrok 或 X Premium+） |

工具裝在非標準位置時，用環境變數指定：`TEAMAI_CODEX_BIN`、`TEAMAI_GEMINI_BIN`、`TEAMAI_GROK_BIN`、`TEAMAI_AGY_BIN`。

裝好之後一定跑一次 `<panel> --selftest`。實測紀錄（2026-11，macOS）：Codex 0.169、agy 1.5.12、Grok 1.0.89 都擋得住寫檔。agy 和 Grok 被擋之後整輪直接結束、不輸出內容，自我測試是看它們自己紀錄裡的拒絕訊息判定的：一般要同一行提到 `proof.txt` 與寫入動作；agy 的訊息不帶檔名，另外認它的「write_file 或 command 權限被自動拒絕」這個格式。Grok 在無人看管時只要叫了需要核准的工具（寫檔、上網），整輪就直接結束而且回報成功，所以腳本只給它讀檔工具。Google 這一家 agy 沒成功時（例如沒登入），腳本會自動換 gemini 再試一次。
