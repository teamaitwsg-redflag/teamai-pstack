# 信任曲線

自動化的程度要跟著證據一階一階往上，沒有捷徑。每一階都有可以檢查的條件，沒達到就不往上走。

## 六階

| 階 | 做法 | 升到這一階要看到的證據 |
|---|---|---|
| 1 | 單一 AI，人全程看著，記下它在哪裡出錯 | 有一份錯誤紀錄（檔案、issue 或 CLAUDE.md 裡的條目），不是只留在對話裡 |
| 2 | 把重複的錯變成硬規則 | 有 linter 或格式檢查的設定；有 CI，而且 PR 沒過 CI 不能合併；至少有一條規則是從階 1 的錯誤來的 |
| 3 | 交件必須附證據 | 專案有可以一行指令跑完的測試；近期的 PR 說明裡有測試輸出、截圖或錄影 |
| 4 | 同時開兩三個 AI，寫的和審的分開 | PR 的審查者不是作者；有固定的審查做法（`/pstack:interrogate`、跨廠牌第二眼）；平行工作用分支或 worktree 隔開 |
| 5 | 睡前交辦任務，AI 開 PR 但不能自己合併 | 任務單有明確的完成條件與停損條件（`/teamai:overnight`）；過夜的工作留有決策紀錄；預設分支有保護，AI 的帳號不能直接推 |
| 6 | 過夜的 PR 自動合併、自動進單 | 階 5 連續一段時間的 PR 都不需要人修改就能合併；合併前有多個沒參與實作的 AI 實測（`/pstack:swarm`）；有回復的辦法，而且試過 |

## 檢核做法

1. 實際去看 repo，不要用問的代替查的：
   - CI：`.github/workflows/`、其他 CI 設定檔。
   - linter 與格式：`eslint`、`ruff`、`biome`、`.pre-commit-config.yaml` 等設定檔。
   - 測試：測試目錄、`package.json` 的 scripts、`pyproject.toml`。實際跑一次，記下結果與時間。
   - 規則與錯誤紀錄：`CLAUDE.md`、`AGENTS.md`、`docs/`。
   - PR 習慣：最近十個已合併的 PR，看作者、審查者、說明裡有沒有證據。
   - 分支保護：查得到就查，查不到就列為「需要使用者確認」。
2. 一階一階往上對。某一階有一項條件沒達到，目前就停在前一階，不看更高的階有沒有零星做到。
3. 每一項判定都附上你看到的東西（檔案路徑、指令輸出、PR 連結）。沒查到的寫「沒查到」，不要寫「沒有」。

## 回報格式

```
目前在第 N 階：一句話說明
已達到：（條列，附證據）
升到第 N+1 階還缺：（條列，每項寫出具體要加的檔案或設定）
建議先做的一件事：
需要使用者確認的事：（我查不到的設定）
```

## 界線

- 還沒到第 5 階，不建議過夜放行。還沒到第 6 階，不建議自動合併。使用者堅持要開時，把缺少的條件和會發生的事講清楚，由他決定。
- 不替使用者修改分支保護、合併設定或 CI 權限。那些由使用者自己動手，或在他明確要求後才做。
- 補硬規則時用 `/pstack:correct`，每次只加一條，加完確認它真的擋得住那個錯。
