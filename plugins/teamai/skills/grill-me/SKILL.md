# 需求釐清

目標是在寫第一行程式之前，把「做什麼、不做什麼、怎樣算做完」問到可以條列。這一步省下的是後面整輪重做。

## 做法

1. 先讀現有的東西再問。repo 裡查得到的事（用什麼框架、有沒有類似功能、資料長什麼樣）自己查，不要拿去問使用者。
2. 一次只問一個問題，等回答再問下一個。能給選項就給選項，並說你建議哪一個、為什麼。
3. 每個問題都要是「答案會改變做法」的問題。答案不影響做法的不問，自己選合理的預設，最後列在「我替你決定的事」。
4. 使用者回答含糊時，用具體例子逼出邊界：「如果使用者輸入空白，要擋下來還是當成零？」
5. 問到下面五項都能寫出來就停。通常三到七個問題。使用者說「夠了，開始做」就停。

## 要問出來的五項

- 使用者是誰，他現在怎麼做這件事，痛在哪裡。
- 這次要做的範圍，以及明確不做的事。
- 驗收條件：可以客觀判斷通過或不通過的條列，每一條都對應得到一個測試或一個實際操作。
- 限制：期限、不能動的既有行為、要相容的資料或介面、效能與費用上限。
- 做錯的代價最高的地方在哪裡（金額、資料遺失、對外發送）。

## 產出

問完後給一份需求摘要，請使用者確認：

```
目標：一句話
使用者與情境：
範圍：
不做：
驗收條件：
  1. …（怎麼驗）
  2. …
限制：
風險最高的地方：
我替你決定的事：（使用者沒指定、我選的預設，可以推翻）
還沒有答案的問題：
```

使用者確認後，接 `/pstack:sharpen` 或直接進實作（`/pstack:tdd`、`/pstack:poteto-mode`）。驗收條件原封不動帶過去，做完用 `/teamai:evidence` 逐條對。
