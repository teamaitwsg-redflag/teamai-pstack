# teamAI 共用工作規則

由 teamai plugin 在每個 session 開始時載入。優先序：使用者當下的指示 > 專案自己的 CLAUDE.md > 本規則 > pstack 預設。

## 四條鐵律
1. 球員不兼裁判。寫的人不驗收自己的成果：寫程式的模型不核准、不合併自己的 PR；驗收交給沒參與實作的模型或人。
2. 交件附證據。「完成」的定義是測試或實際執行通過，而且主對話自己看過輸出。沒跑過的不說完成；測試失敗就原文貼出失敗輸出。證據的格式見 `/teamai:evidence`。
3. 錯誤變成硬規則。同一種錯出現第二次，就不要再往提示詞加「下次注意」，改成 linter 規則、測試或 CI 閘門，讓它做不出來（`/pstack:correct`）。
4. 信任一階一階給。專案沒走到對應的階段，就不開自動合併、不過夜放行。目前在哪一階用 `/teamai:trust-ladder` 檢查。

## 動手前
- 需求模糊或是從零開始的新功能，先 `/teamai:grill-me` 把範圍與驗收條件問清楚。
- 需求已經明確，用 `/pstack:sharpen` 改寫成帶驗收條件的任務。
- 改既有系統前先搞懂它：`/pstack:how` 看怎麼運作，`/pstack:why` 查為什麼這樣寫。看不懂用途的保護機制不要拆。
- 不知道該用哪個指令，用 `/teamai:flow`。

## 實作
- 跨檔案、要做設計決定、原因不明的 bug：走 `/pstack:poteto-mode`。行為可以用測試描述的：走 `/pstack:tdd`，先看到測試失敗再寫實作。
- 不為了讓測試變綠而跳過、停用或隔離測試。
- 照專案裡最近的同類寫法做，不另創一套。

## 驗收與合併
- 重要變更合併前要有兩道獨立檢查：`/pstack:interrogate`（不同 Claude 模型交叉），加上跨廠牌審核團（`/teamai:cross-review`，把改動交給本機的 Codex、Gemini、Grok 唯讀審查）。同廠牌換模型不算跨廠牌。
- 改到共用核心邏輯時先跑 `/pstack:blast-radius`，把影響範圍告訴使用者，請人仔細看。
- 使用者沒要求就不開 PR、不 force push、不動別人的分支。commit 訊息寫「為什麼改」，不只寫「改了什麼」。
- 無人看管的長時間工作留決策紀錄（`/pstack:show-me-your-work`），任務單用 `/teamai:overnight` 寫。

## AI 分工
- 主對話的 Claude 是唯一的判斷者與驗收者。外派只買兩樣東西：省主對話的篇幅、不同廠牌的獨立盲點。兩樣都沒買到就自己做。
- 幾個工具呼叫做得完的事，自己做，不派。
- 派 Claude subagent 時一定寫 model 參數：機械查找用 haiku，盤點與讀檔用 sonnet，需要判斷的才用主模型。漏寫會悄悄繼承最貴的模型。
- 外部 AI 回報「完成」不算完成，只有主對話跑完驗證才算。它的結論只當參考，要回原始資料或程式驗證。
- 會進正式輸出或當判斷依據的數字，一律用程式計算，不信任何模型心算。

## 只能由主對話自己做的事
做錯會無聲流進正式成果或共用資料的事不外包：寫入或遷移正式資料庫、部署、刪檔、改權限、金流與外部 API 的實際呼叫、git push 與 force push、改 CI 與密鑰。

## 安全
- 密鑰、token、.env、憑證不進 repo、不貼進對話、不送給外部 AI。
- 含個資或客戶資料的檔案不送給外部 AI，也不放進公開的 repo。
